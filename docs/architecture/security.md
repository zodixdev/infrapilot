# Security Architecture & Threat Model

## 1. Identities

| Principal | Authentication | Authorization |
|---|---|---|
| Human user | Keycloak OIDC (Auth Code + PKCE); gateway validates JWT via JWKS | RBAC per org: `owner`, `admin`, `operator`, `viewer`; `control-plane.CheckPermission` (cached 30 s in Redis) |
| API client | Project-scoped API key (`ipk_` prefix, stored as SHA-256 hash, shown once) | Scopes on the key (`ingest`, `read`, `write`) |
| Agent | mTLS client cert issued by agent-manager internal CA after one-time enrollment token; 24 h cert TTL, auto-rotated at 2/3 lifetime | Bound to one org + resource; can only receive commands for itself |
| Service | Kubernetes ServiceAccount + TLS (cert-manager); gRPC interceptors verify peer identity allow-list | Per-RPC allow-list of calling services |

Role/permission matrix, API-key scopes and enforcement points: ADR-0022. Service identities and how the end-user
principal reaches internal services: ADR-0025. Gateway JWKS/rate-limit/cache behavior: ADR-0026.

## 2. Remote actions (highest-risk feature)

- Agents execute **only allow-listed action types** (e.g. `restart_systemd_unit`, `collect_diagnostics`,
  `run_healthcheck`) with typed, validated parameters. **No arbitrary shell.**
- Commands are created by workflow-engine, require policy evaluation + human approval for sensitive types,
  and are signed with Ed25519 (key in a Kubernetes Secret, rotated, `kid` in the command).
- Agent verifies signature, `agent_id`, `expires_at` (≤ 5 min), and a nonce (replay cache).
- Every request, approval, execution and result is written to the append-only audit log.
- AI output can **suggest** actions; it cannot create approved commands.

## 3. SSRF protection (check-runner)

Custom `net.Dialer.Control` that rejects connections to: loopback, RFC1918, CGNAT (100.64/10), link-local
(169.254/16 incl. cloud metadata), IPv6 ULA/link-local, multicast, and cluster CIDRs. Validation runs on
the **resolved IP at connect time** (defeats DNS rebinding), redirects are limited (≤5) and re-validated,
response bodies are size-capped, timeouts are mandatory. Check workers run in a dedicated namespace with
an egress NetworkPolicy blocking cluster-internal ranges.

## 4. STRIDE summary

| Threat | Example | Mitigation |
|---|---|---|
| Spoofing | Fake agent sends telemetry | mTLS + enrollment token, cert bound to org/resource |
| Tampering | Modified command in transit | Ed25519 signatures + TLS |
| Repudiation | "I didn't approve that restart" | Append-only audit log with actor, time, request ID |
| Information disclosure | Cross-tenant data leak | RLS + repo-level tenant scoping + tests; query-service filter injection |
| Denial of service | One tenant floods ingestion | Per-tenant quotas, rate limits, bounded queues, Kafka backpressure |
| Elevation of privilege | Viewer triggers a workflow | RBAC checks server-side on every mutation; policy engine for actions |
| SSRF | Check pointed at 169.254.169.254 | §3 |
| Prompt injection | Log line tells the LLM to run a command | LLM output is untrusted text; no tool execution; schema-validated output |

## 5. Secrets

Local: `.env` (git-ignored), generated by `make secrets`. Kubernetes: Secrets created from
External Secrets Operator in prod; never in Helm values committed to git. No secrets in logs
(slog `ReplaceAttr` redaction for known keys). `gitleaks` runs in CI and in the pre-commit hook.

## 6. Supply chain

Pinned base images (distroless/static for Go), non-root, read-only root FS. `govulncheck`, `trivy`
image scan, `gitleaks`, dependency review in CI. SBOM generated per image (syft).
